# Сценарий демо (≈2 минуты)

Три кейса из набора QA (`qa/cases.csv`): чистый, неполный и с ошибкой. Все три проверены на текущей версии `main` с индексом `catalog.db` (запрос `POST /api/analyze` с `domain_hint`), скорость: медиана ~50 мс, в демо 100–200 мс, первый запрос до 0,5 с. Перед показом: запустить `uvicorn app.main:app --port 8000`, открыть http://localhost:8000.

Важно для ведущего: воронка заканчивается не одним кодом, а группой из 2–3 вариаций одного наименования. Это нормально: код КТРУ определяется до наименования, а различия между вариациями задают обязательные характеристики, которые мы и просим заполнить.

Пустые строки в таблице без пометки «обязательная» — необязательные: их можно оставить пустыми, на статус карточки они не влияют.

## Кейс 1. Чистый ввод — FU19, кресло офисное

**Ввод (домен «мебель»):**
```
Кресло офисное обивка ткань цвет черный высота 1080 мм ширина 650 мм глубина 450 мм
```

**Что видит зал:**
- Статус `ok`, лучший код **31.01.12.160-00000005 «Кресло офисное»**.
- Воронка: **355 → 2 → 2 → 2** (Домен → Наименование → ОКПД2 → Итог), у каждого шага причина.
- Таблица: Высота 1080 мм, Ширина 650 мм, Глубина 450 мм, Цвет черный — бейдж **Портал**.
- Две строки с бейджем **КТРУ**: «Вид материала обивки спинки» и «Вид материала обивки сиденья» — обязательные для кода; из слов «обивка ткань» ядро уже подставило в обе значение «Текстиль».
- Бейджи: **Код: определён**, **Карточка: заполнена**, строка «2/2 обязательных, 4/7 необязательных». Три необязательные строки (среди них «Вид материала крестовины») пустые и без пометки «обязательная» — их можно не заполнять (в «Что сделать дальше» они серым, «необязательно»; на `main` — обычными пунктами).
- Блок «Было → стало» (только на `main`): «автоисправление: ткань → Текстиль» для обеих обивок; на ядре из `feature/core` этот блок для FU19 не показывается.

**Что делаем:** в таблице уточняем «Вид материала обивки спинки» = «Ткань сетчатая армированная», «Вид материала обивки сиденья» = «Экокожа» (варианты из списка КТРУ).

**Результат после пересчёта:** замечаний нет, в воронке появляются шаги по двум новым характеристикам (355 → 2 → 2 → 2 → 2 → 2), код тот же.

## Кейс 2. Неполный ввод — TO37, «Ключ»

**Ввод (домен «инструменты»):**
```
Ключ
```

**Что видит зал:**
- Статус `need_more`, лучший код **25.73.30.171-00000001 «Ключ гаечный разводной»**.
- Воронка: **1514 → 3 → 3 → 3**.
- Подсказки: «Не удалось выделить характеристики из текста» с примером формата и обязательная характеристика КТРУ «Тип исполнения» (пустая строка с бейджем **КТРУ**, допустимое значение «B»).
- Бейджи: **Код: определён**, **Карточка: не хватает обязательных: 1**, «0/1 обязательных, 0/2 необязательных». На `feature/core` в «Что сделать дальше» первым идёт обязательный «Укажите: Тип исполнения», ниже серым — необязательные «Диэлектрическое покрытие» и «Длина разводного ключа».

**Что делаем:** заполняем «Тип исполнения» = «B».

**Результат:** статус `ok`, бейдж **Карточка: заполнена** («1/1 обязательных, 0/3 необязательных»), воронка **1514 → 3 → 3 → 2 → 2**, характеристика сузила коды, замечаний нет.

## Кейс 3. Ввод с ошибкой — TO42, нереалистичная длина

**Ввод (домен «инструменты»):**
```
Ключ гаечный 170х190 мм длина 27 м
```

**Что видит зал:**
- Статус `error`, код **25.73.30.171-00000001 «Ключ гаечный разводной»** (верная группа найдена несмотря на ошибку).
- Воронка: **1514 → 3 → 3 → 3 → 3** (шаг «длина»: коды не отсеяны — ошибочное значение не фильтрует, а подсвечивается).
- Ошибка: ««длина» = 27 м нереалистично для ручного инструмента (больше 3 м)», ожидается «до 3 м», варианты «27 мм», «27 см». В таблице значение пересчитано в единицу КТРУ: 27000 мм.
- В превью под полем описания фрагмент **«27 м»** подсвечен красным, при наведении — текст ошибки.
- Бейджи: **Код: определён**, **Карточка: есть ошибки**, «0/1 обязательных, 1/2 необязательных».
- Блок «Было → стало»: «единицы · Длина разводного ключа: длина 27 м → 27000 мм» (на `feature/core` — «27 м → 27000 мм»).
- Плюс незаполненная обязательная строка «Тип исполнения» (пометка «обязательная · заполните», допустимо «B») и пункт «Укажите: Тип исполнения» в «Что сделать дальше». На `feature/core` пункт «Исправьте «длина»: 27 мм» стоит среди необязательных (серым) — это поведение ядра, на `main` все пункты обычные.

**Что делаем:** в поле описания исправляем «27 м» на «270 мм» (правку делаем именно в тексте — так надёжнее для демо), затем заполняем «Тип исполнения» = «B».

**Результат:** после исправления длины ошибка исчезает (остаётся только незаполненный «Тип исполнения»), после заполнения — статус `ok`.

## Текст для ведущего (~2 минуты)

> Поставщик пишет описание товара как привык — одной строкой. Покажу три случая.
>
> Первый — нормальное описание кресла. Сервис за доли секунды разобрал строку: высота, ширина, глубина, цвет. Бейдж «Портал» значит, что такие характеристики есть в карточках портала. Справа воронка: из 355 кодов мебели по названию осталось два — оба «Кресло офисное». Но система видит, что у этого кода КТРУ есть две обязательные характеристики — материал обивки спинки и сиденья. Они уже стоят в таблице с бейджем «КТРУ». Заполняю из допустимых значений — замечаний нет, карточка готова.
>
> Второй случай — поставщик написал одно слово «Ключ». Мы не угадываем: статус «нужно уточнение», показываем три подходящих кода и говорим, чего не хватает — обязательный «Тип исполнения». Заполняю — воронка сужается с трёх кодов до двух, статус «ок».
>
> Третий — ошибка: длина ключа 27 метров. Группу кода мы всё равно нашли верно, но выдаём ошибку: для ручного инструмента это нереалистично, и предлагаем варианты — 27 миллиметров или сантиметров. Обратите внимание: ошибочное значение не выкидывает коды из воронки, а подсвечивается. Исправляю на 270 миллиметров — ошибка ушла.
>
> Итог: каждая характеристика привязана к источнику — КТРУ, портал или новая, каждое сужение объяснено, а ошибки ловятся до отправки карточки. По прогону QA на 45 кейсах: верный код на первом месте в 96% случаев и в топ-3 — в 100%, ложно-уверенных ответов на ошибочном вводе — ноль.
