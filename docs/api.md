# API `POST /api/analyze`

## Запрос

| Поле | Тип | Описание |
|---|---|---|
| `text` | string, обязательно | Свободное описание товара |
| `characteristics` | `[{name, value, unit}]` \| null | Строки таблицы из UI; перекрывают распознанные из текста с тем же каноническим именем |
| `domain_hint` | `furniture` \| `clothing` \| `tools` \| null | Подсказка домена; другое значение → HTTP 422 |

Ошибки запроса → **HTTP 422**: пустой или отсутствующий `text` (`min_length=1`), неизвестный `domain_hint`,
неверные типы полей.

## Ответ

| Поле | Тип | Описание |
|---|---|---|
| `input_text` | string | Исходный текст |
| `detected_domain` | string \| null | Домен |
| `product_guess` | string \| null | Распознанное наименование (после исправления опечаток) |
| `best_ktru` | object \| null | `{code, name, okpd2, score, required_chars[], matched_chars[]}` |
| `candidates` | `[{code, name, score}]` | До 5 кандидатов, если подходит несколько |
| `status` | string | Старое поле (для совместимости): `not_found` > `error` > `need_more` > `ambiguous` > `ok` |
| `code_status` | `determined` \| `ambiguous` \| `not_found` | Уверенность в коде: `determined` — все оставшиеся кандидаты — вариации одного наименования |
| `card_status` | `complete` \| `incomplete` \| `invalid` | Заполненность карточки: `invalid` — есть ошибки (severity=error), `incomplete` — пусты обязательные характеристики или ничего не распознано |
| `completeness` | object | `{required_total, required_filled, optional_total, optional_filled}` по таблице `characteristics` |
| `characteristics` | array | Таблица характеристик, см. ниже |
| `issues` | array | Проблемы, см. ниже |
| `corrections` | array | Что ядро исправило само, см. ниже |
| `narrowing` | array | Шаги сужения, см. ниже |
| `next_steps` | string[] | Только обязательные шаги (обязательные характеристики и шаги без поля, например «уточните тип товара») |
| `next_steps_detail` | `[{text, field, required}]` | Все шаги; `field` — имя строки таблицы или null |
| `missing_characteristics` | array | **Полный** список незаполненных характеристик выбранного кода (любое n): сначала обязательные, затем необязательные. `[{name, required, allowed, min, max, unit}]` |
| `fill` | object \| null | Счётчик по характеристикам КТРУ выбранного кода: `{filled, total, required_filled, required_total, text}`, `text` = «Заполнено X из Y характеристик КТРУ (обязательных a из b)». `null`, если кода нет или у позиции КТРУ нет характеристик (тогда `message` = «У позиции КТРУ нет характеристик») |
| `question` | object \| null | Уточняющий вопрос, **только** когда выбор нельзя сделать за пользователя, см. ниже. Иначе null — UI просто подсвечивает поля |
| `out_of_scope` | bool | `true` — «не наша категория»: товар не из мебели/одежды/инструментов (или не распознан). Тогда `status = not_found`, `best_ktru = null`, `message` объясняет, плюс issue `type = out_of_scope` |
| `message` | string \| null | Текст «не наша категория» при `out_of_scope = true`, либо «У позиции КТРУ нет характеристик» |
| `debug` | object | `{raw_count, elapsed_ms}` |

### `characteristics[]`

| Поле | Тип | Описание |
|---|---|---|
| `name` | string | Каноническое имя (КТРУ → портал → новое свойство) |
| `value` | string | Значение (пустая строка — не заполнено) |
| `unit` | string \| null | Единица (для числовых КТРУ — единица КТРУ) |
| `source` | `ktru` \| `portal` \| `new` | Источник имени |
| `user_input` | string \| null | Фрагмент ввода, из которого взято значение |
| `required` | bool | Обязательная характеристика КТРУ |
| `allowed` | string[] \| null | Допустимые значения (только перечисления) |
| `min`, `max` | number \| null | Диапазон числовой характеристики в `unit` |
| `span` | `[start, end]` \| null | Смещения символов в исходном `text`, если значение взято из текста |
| `suspicious` | bool | Характеристика не подходит к типу товара («мощность» у гаечного ключа); к ней есть issue `mismatch`/`warning` |
| `raw_name`, `canonical_name`, `confidence`, `notes` | — | Служебные/устаревшие |

### `issues[]`

| Поле | Тип | Описание |
|---|---|---|
| `type` | string | `not_allowed`, `out_of_range`, `unit`, `mismatch`, `missing`, `typo`, `ambiguous`, `new_property`, `out_of_scope` |
| `kind` | string | То же, что `type` (совместимость) |
| `field` | string \| null | Характеристика |
| `value`, `expected` | string \| null | Введённое и ожидаемое значение |
| `suggestions` | string[] | До 3 подсказок (`suggestion` — первая, совместимость) |
| `message` | string \| null | Текст «не наша категория» при `out_of_scope = true`, либо «У позиции КТРУ нет характеристик» |
| `severity` | `error` \| `warning` | `new_property` всегда `warning` |
| `span` | `[start, end]` \| null | Смещения в исходном `text` |

### `corrections[]`

| Поле | Тип | Описание |
|---|---|---|
| `field` | string \| null | Характеристика или «Наименование» |
| `kind` | `unit` \| `autofix` \| `typo` \| `translit` | `unit` — перевод/подстановка единицы («27 см» → «270 мм», «750» → «750 мм»); `autofix` — значение исправлено на допустимое КТРУ (нечёткое совпадение ≥ 92, «чорный» → «Черный»); `typo` — исправлено слово в наименовании; `translit` — латиница → кириллица |
| `from`, `to` | string | Было → стало |
| `span` | `[start, end]` \| null | Где в исходном `text` |

### `span`: характеристики и исправления

- `characteristics[].span` — где в исходном `text` находится **весь фрагмент**, из которого взято значение
  (имя + значение + единица, как в `user_input`, например «длина 27 см»). Для строк из UI и пустых строк — null.
- `corrections[].span` — где находится **только исправленный фрагмент** (`from`, например «27 см»).
  Поэтому span исправления обычно лежит внутри span характеристики.
- `issues[].span` — фрагмент, к которому относится проблема (значение или имя поля), иначе null.
- Смещения — индексы символов Python/JS-строки: `text.slice(start, end)`. При вводе латиницей ядро
  работает с транслитерацией, и span может быть null.
- Опечатки вне наименования товара приходят в `issues`/`corrections` с `field = "Описание"`.

### Порядок и полнота `characteristics[]`

- Порядок всегда: **КТРУ → портал → новые свойства**; подозрительные (`suspicious`) — в конце.
  Внутри КТРУ: заполненные, затем пустые обязательные, затем пустые необязательные.
- Для выбранного кода в таблице есть **все** его характеристики КТРУ, включая пустые необязательные.
  `allowed` заполнен везде, где у КТРУ есть перечисление (и у пустых строк), у числовых — `min`/`max`/`unit`.
- Синонимы имён сводятся к одной характеристике: «вес 500 г» и «масса 500 г» → «Масса молотка».
  Новые свойства получают единую формулировку: регистр, «ё», синонимы, главное слово первым
  («корпуса цвет» → «Цвет корпуса»).
- Подозрительная характеристика: величина, которой нет ни у одной позиции КТРУ этой группы ОКПД2
  (мощность, напряжение, ток, ёмкость АКБ, обороты, момент, частота — например, у ручного ключа).
  Не применяется к классам ОКПД2 28.x (28.24 — электроинструмент, машины), а для
  электро-/пневмо-/аккумуляторного инструмента и машин эти величины считаются нормальными.
  Она не заводится как новое свойство: `suspicious = true` и issue
  `{type: "mismatch", severity: "warning", message: "Характеристика не подходит к типу товара: …"}`.
- Отрицательные значения («высота -750 мм») не отбрасываются: ошибка `out_of_range`/`mismatch`, severity `error`.

### Очистка ввода и `span`

HTML-теги (и содержимое `<script>`/`<style>`) заменяются пробелами той же длины, невидимые символы
(zero-width, мягкий перенос) удаляются, после чего смещения пересчитываются обратно.
Все `span` **указывают в исходный `text`** (`input_text`), а не в очищенный.

### `question`

`{field, reason, options[], remaining_by_option{option: n}, candidates_now}` — `options` не больше 6,
только значения из КТРУ; `remaining_by_option` — сколько кодов останется после выбора варианта.
Вопрос задаётся, только если подходящие коды имеют разные наименования или их различает незаполненная
**обязательная** характеристика-перечисление. Иначе `question = null`.

### `narrowing[]`

`{step, label, remaining, removed, reason, removed_codes[]}` (+ устаревшие `stage`, `top[]`, `note`).
`label`: «Домен», «Наименование», «ОКПД2», имя характеристики, «Итог». Первый шаг — начальный пул (`remaining` = N).

## Пример (фрагмент)

Запрос `{"text": "Ключ гаечный 17х19 мм длина 27 см цвет чорный"}`:

```json
{
  "status": "need_more", "code_status": "determined", "card_status": "incomplete",
  "completeness": {"required_total": 1, "required_filled": 0, "optional_total": 3, "optional_filled": 2},
  "corrections": [{"field": "Длина разводного ключа", "kind": "unit", "from": "27 см", "to": "270 мм", "span": [28, 33]}],
  "next_steps": ["Укажите: Тип исполнения"],
  "next_steps_detail": [
    {"text": "Укажите: Диэлектрическое покрытие", "field": "Диэлектрическое покрытие", "required": false},
    {"text": "Укажите: Тип исполнения", "field": "Тип исполнения", "required": true}

```

# Пакетная обработка

Лимит — 500 строк за запрос (больше → **413**). Строки обрабатываются тем же движком, что и
`/api/analyze` (пул из 4 потоков), порядок результатов совпадает с порядком входа. Ошибка в одной
строке не ломает пакет: строка приходит как `{id, text, error}`.

## `POST /api/analyze/batch` (JSON)

```json
{"items": [{"id": 1, "text": "Стол письменный ЛДСП"}, {"id": "a2", "text": "Молоток слесарный"}],
 "domain_hint": null}
```

`id` необязателен (по умолчанию номер строки с 1). Ответ:

```json
{
  "results": [
    {"id": 1, "text": "Стол письменный ЛДСП", "...": "полный ответ /api/analyze"},
    {"id": 3, "text": "", "error": "Пустое наименование"}
  ],
  "summary": {
    "total": 3, "errors": 1,
    "by_code_status": {"determined": 1, "ambiguous": 0, "not_found": 0, "out_of_scope": 1},
    "by_card_status": {"complete": 0, "incomplete": 2, "invalid": 0},
    "by_status": {"ok": 0, "need_more": 1, "ambiguous": 0, "error": 0, "not_found": 1},
    "elapsed_ms": 140.2
  }
}
```

`by_code_status`: строка с `out_of_scope = true` считается в `out_of_scope` (а не в `not_found`);
строки с `error` не входят в `by_*`. `by_status` — по старому полю `status`.

## `POST /api/analyze/csv` (multipart)

Поле `file` — CSV с одним столбцом наименований. Необязательный query-параметр `domain_hint`.
- Кодировка: UTF-8 (с BOM или без), иначе cp1251.
- Разделитель: `;` или табуляция; `,` — только если значения в кавычках. Файл без кавычек и без `;`
  читается построчно, запятые остаются частью наименования.
- Заголовок необязателен: распознаётся по `name`/`наименование`/`название`/`товар`/`text`/`query`/`описание`;
  при заголовке можно добавить столбец `id`. Пустые строки пропускаются.
- Пустой файл → 422; больше 500 строк → 413; файл > 5 МБ → 413.

Ответ — как у `/batch`, плюс `file: {name, encoding, delimiter, header, rows}`.

## Потоковый режим (NDJSON)

`?stream=1` или заголовок `Accept: application/x-ndjson` у обоих эндпоинтов. Ответ
`Content-Type: application/x-ndjson`, по строке JSON на каждую входную строку, в порядке входа:

```
{"type": "result", "id": 1, "text": "...", ...полный ответ /api/analyze...}
{"type": "result", "id": 2, "text": "", "error": "Пустое наименование"}
{"type": "summary", "summary": {...как выше...}, "file": {...только для csv...}}
```

Последняя строка всегда `type = summary`. UI: сначала `/api/analyze/batch?stream=1`, при ошибке —
`/api/analyze/batch`, затем построчно `/api/analyze`.

Замер (Windows, Python 3.11, 1 процесс uvicorn, `qa/batch100.csv`, 100 строк): JSON-пакет ~3.9 с,
NDJSON ~3.7 с (первая строка через ~0.35 с), CSV cp1251 ~3.9 с; по одной строке через `/api/analyze` — ~7.3 с.
